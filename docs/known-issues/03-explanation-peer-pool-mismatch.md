# Finding 3: The "why" explanation doesn't use the same similar-teams pool as the recommendation

**Status: Resolved.** `get_recommendation_explanation()` now accepts `k_similar`/`min_similarity_threshold` params (defaults 19/0.75, matching `recommend()`) and every call site threads through the same values used for the corresponding `recommend()` call. See `src/ml/recommender.py`, `src/api/service.py`, `src/interface/cli.py`, `scripts/analyze_month_predictions.py`, and the strengthened peer-pool assertion in `tests/test_temporal_boundaries.py::test_no_future_similar_teams_in_explanation`.

## Problem statement (user perspective)

When the system gives you a recommendation, it also shows a human-readable explanation — something like "similar teams that improved this practice were X, Y, Z." The intent is for this explanation to justify the score: it should be built from the same pool of similar teams that actually produced the recommendation.

In practice, it isn't. The recommendation itself is computed using a carefully filtered set of similar teams — up to 19 of them, and only ones that clear a fairly high similarity bar (0.75 out of 1.0). But the explanation text is generated by a separate lookup that pulls just 5 similar teams, with **no similarity bar applied at all**.

Consequences:
- The teams named in the "why" explanation are not guaranteed to be the same teams that actually influenced the score. The explanation can name a team that had little in common with yours and had zero real influence on the number shown.
- If someone asks "show me exactly which similar teams drove this recommendation," the displayed explanation may not be a literally accurate answer — it tells a plausible-sounding story, not necessarily the true one.
- This is a UI-trust issue rather than a scoring bug: the recommendation's score itself is computed correctly and is unaffected by this — only the justification text shown alongside it can be inconsistent with how the score was actually produced.

## Technical detail

- **File**: `src/ml/recommender.py`
- **Recommendation path** (`recommend()`, line 143): finds similar teams with
  ```python
  self.similarity_engine.find_similar_teams(
      target_team, current_month, k=k_similar, min_similarity=min_similarity_threshold
  )
  ```
  using the caller's configured `k_similar` (default 19) and `min_similarity_threshold` (default 0.75).
- **Explanation path** (`get_recommendation_explanation()`, line 362): finds similar teams with
  ```python
  similar_teams = self.similarity_engine.find_similar_teams(target_team, current_month, k=5)
  ```
  — a fixed `k=5`, and no `min_similarity` argument at all, so it silently defaults to `0.0` (no filtering).
- The two calls can return different, only-partially-overlapping sets of teams for the same `(target_team, current_month)` pair, so the explanation is describing a different peer pool than the one that actually produced the score.

## Suggested fix

Make `get_recommendation_explanation()` use the same similarity search parameters as `recommend()`, so the explanation is always describing the actual peer pool behind the score:

```python
similar_teams = self.similarity_engine.find_similar_teams(
    target_team, current_month, k=k_similar, min_similarity=min_similarity_threshold
)
```

This requires `get_recommendation_explanation()` to accept (or be passed) the same `k_similar` and `min_similarity_threshold` values that were used for the original `recommend()` call, rather than hardcoding its own smaller, unfiltered lookup.
